Provenance of the uncatalogued-allele search
============================================

The release manifest records the environment that wrote it, which is not the
environment every stage of this search ran in. The two are set out here so the
manifest cannot be read as a claim it does not support.

Stages that called genes and aligned them
-----------------------------------------
  scripts/28_allele_search.py    -> results/allele_search/hits.jsonl
  scripts/29_short_orf_check.py  -> results/allele_search/short_orfs.jsonl
  scripts/30_fragment_loci.py    -> results/allele_search/fragment_loci.jsonl

  ran on   Linux-6.8.0-138-generic-x86_64-with-glibc2.35
  python   3.10.12
  pyrodigal 3.7.1
  pyswrd    0.3.1

These three stages read the assemblies, which are 19 GB and are not part of the
release, so they were run where the assemblies are held. They use pyrodigal and
pyswrd only. They import none of numpy, scipy, pandas, scikit-learn,
statsmodels or matplotlib, so the pins for those packages do not bear on their
output.

Stage that screens with profiles
--------------------------------
  scripts/35_profile_screen.py   -> results/allele_search/profile_hits.jsonl

Added 19 October 2026. It reads the assemblies for the same reason as the three
stages above and ran in the same environment, with pyhmmer 0.12.3 in addition
to pyrodigal. It imports none of the pinned scientific packages either.

The profile library it reads is built by scripts/34_build_betalactamase_profiles.py
from AMRProt.fa alone, so it needs no assemblies and carries the same
provenance as the reference set. It was built in both environments, under
python 3.10.12 with pyfamsa 0.7.0 and pyhmmer 0.12.3 and under python 3.13.16
with the same two packages, and the family table comes out byte-identical:

  results/allele_search/ref/betalactamase_families.tsv
  sha256 92f9d24e347a38293e6fad427c61e075...

The .hmm file itself carries a build timestamp in its header, so it is not
byte-identical between runs and the family table beside it is what the
reproducibility claim rests on.

Stages that build the tables
----------------------------
  scripts/31_allele_search_summary.py -> results/supplementary/S19a_allele_search_summary.tsv
  scripts/32_allele_search_tables.py  -> results/supplementary/S19b_carbapenemase_gene_fragments.tsv
                                         results/supplementary/S19c_allele_search_per_genome.tsv
  scripts/36_profile_screen_summary.py -> results/tables/profile_screen_summary.tsv
                                         results/tables/profile_screen_unmatched_proteins.tsv
  scripts/33_detection_floor.py       -> results/tables/allele_search_detection_floor.tsv

These read only the three .jsonl files and carb_calls.json, and they were run
in both environments. Under python 3.10.12 above and under python 3.13.16 with
every requirements.txt pin satisfied, all three tables come out byte-identical,
verified by sha256. The classification itself lives in
scripts/allele_classify.py and is reapplied from the stored identity and
coverage each time a table is built, so the tables do not depend on the verdict
written during the original run.
